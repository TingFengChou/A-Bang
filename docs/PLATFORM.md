# 阿幫平台（下一階段規格草案）

狀態：構想 v0.1（2026-11-17）。**本階段不實作**，只要求 M2–M5 預留擴充點（見 §11）。
相關決策：ADR-0005（多 agent 平台）、ADR-0007（平台化與啟動門檻）。

## 1. 一句話

讓任何人——創業者、店家、民宿、一般民眾、外國旅客——都能用**可信的台灣公共資料**，組出自己的 agent，並發布到網頁、LINE、QR code 或 MCP。

## 2. 為什麼不是現在做

平台的價值來自工具包好不好用、護欄可不可靠。沒有先做出 2～3 個自己的 agent 驗證，Builder 只會是空殼。所以順序是：

```
生活 agent（M1–M6）→ 反詐騙 agent（M7）→ 中小企業 agent 概念驗證（M8）→ 達到啟動門檻（§10）→ 阿幫平台（M9）
```

前面每個 agent 都是在累積平台的零件：工具包、卡片、護欄、計量。

## 3. 分層

| 層 | 內容 | 擁有者 |
|---|---|---|
| 工具包（Tool packs） | 一組相關的 MCP tools＋資料來源＋強制護欄＋卡片 | 平台（第一方）；未來可開放認證夥伴 |
| Agent profile | 角色、語言、選用的工具包、知識、建議問題、通路、額度 | 建立者（tenant） |
| Agent 執行環境 | 組合 prompt、tool 迴圈、事件串流、輸出檢查 | 平台 |
| 通路 | 網頁、內嵌對話框、QR code、LINE、MCP 端點、API | 平台提供，建立者選用 |
| 信任層（橫跨各層） | 風險分級、強制護欄、審核、計量、稽核紀錄 | 平台 |

## 4. 使用者與需求

| 使用者 | 需要什麼 | 會自己 build 嗎 | 平台給什麼 |
|---|---|---|---|
| 一般民眾 | 打開就能用 | 幾乎不會 | 第一方 agent（生活、反詐騙）＋輕度個人化（常用路線、住家附近） |
| 創業者／中小企業 | 自己的申辦助理；給客人用的 agent | **會（主要客群）** | Builder、範本、內嵌、QR、分析 |
| 民宿／飯店／旅行社 | 給旅客的多語接待 agent | **會** | 旅宿接待範本、多語、QR code |
| 外國旅客 | 交通、景點、緊急資訊、防詐 | 不會 | 旅客版第一方 agent，或由旅宿建好的 agent |
| 開發者 | 把工具包接進自己的產品 | 用 API / MCP | MCP 端點、API 金鑰、用量儀表板 |
| 政府機關（合作） | 民眾服務、需求洞察 | 共同建置 | 客製工具包、去識別化需求報表 |

## 5. 工具包

### 5.1 規格

```jsonc
{
  "id": "transit",
  "name": { "zh-TW": "交通", "en": "Transit" },
  "version": "1.2.0",
  "owner": "first-party",
  "tier": "L1",                        // 風險分級，見 §5.3
  "tools": ["bus_route_eta", "bus_nearby_stations", "youbike_nearby", "metro_live_board", "thsr_timetable", "tra_timetable", "plan_trip", "find_place"],
  "sources": [{ "name": "交通部 TDX", "license": "政府資料開放授權條款", "attribution": "資料來源：交通部 TDX 運輸資料流通服務" }],
  "guardrails": ["attribution", "freshness"],   // 強制、建立者不可移除
  "languages": ["zh-TW", "en"],
  "costClass": "metered-tdx"
}
```

### 5.2 規劃中的工具包

| 工具包 | 分級 | 主要資料 | 來自哪個階段 |
|---|---|---|---|
| 交通 `transit` | L1（`rail_booking_link` 為 L2） | TDX 公車、捷運、YouBike、台鐵、高鐵、路況、客運；`plan_trip` 決策 | M1–M3 |
| 天氣 `weather` | L1 | 中央氣象署觀測與鄉鎮預報（決策的自動狀態「下雨」） | M3 |
| 叫車 `ridehail` | L2 | 叫車 App 深層連結（先 Uber）；估價待合作（ADR-0011） | M3 |
| 觀光 `tourism` | L1 | TDX 觀光資料（景點、餐飲、旅宿、活動，端點待驗證） | M9 新增 |
| 生活 `life` | L1 | 氣象署、環境部 AQI、健保署藥局 | 候選 |
| 緊急與旅客資訊 `traveler-safety` | L2 | 緊急電話、醫院、駐外單位等（來源待盤點） | M9 新增 |
| 防詐 `antifraud` | L2 | 165 開放資料、詐騙特徵規則庫、111 短碼 | M7 |
| 申辦法規 `permits` | L3 | 法規資料庫、商工登記、人工審核申辦知識庫 | M8 |

### 5.3 風險分級與強制護欄

| 分級 | 定義 | 強制護欄（建立者不可關閉） | 發布審核 |
|---|---|---|---|
| **L1 資訊查詢** | 查即時或公開事實，錯了影響小 | 標示資料來源、資料時間；查不到時明說 | 自動 |
| **L2 判斷建議** | 給風險判斷或建議，錯了可能造成損失 | L1 ＋ 免責聲明；不得做絕對保證（例：不得說「安全」）；高風險時導向官方管道（如 165） | 自動 + 抽樣檢查 |
| **L3 權利義務** | 涉及法規、稅務、申辦等法律效果 | L2 ＋ 每項結論須附法源（條號＋日期）與官方連結；只能引用人工審核的知識庫，不得由模型自行生成義務清單；翻譯版本標示「以中文原文為準」 | 人工審核 |

技術上的保證方式：
1. **Prompt 組裝順序固定**：平台基本政策 → 工具包護欄（依最高分級）→ 建立者的角色與知識（以分隔區塊標示為「資料」）→ 使用者訊息。建立者文字無法覆寫前兩段。
2. **輸出檢查器**：使用 L3 工具的回覆若缺少引用，改為只顯示卡片＋官方連結；L2 回覆含禁止用語（如「保證安全」）則重新生成或改用範本。
3. **建立者知識當資料處理**：上傳的 FAQ／文件以檢索片段引用，不直接拼進 system prompt，降低 prompt injection 風險。

## 6. Agent profile（存成資料）

```jsonc
{
  "id": "xinyi-guesthouse",
  "tenantId": "t_8f2c",
  "status": "draft | in_review | published | suspended",
  "version": 3,
  "name": { "zh-TW": "信義小旅店小幫手", "en": "Xinyi Guesthouse Helper" },
  "template": "guesthouse",
  "persona": "親切的民宿管家，回答交通與周邊景點。",        // ≤ 300 字
  "languages": ["zh-TW", "en", "ja", "ko"],
  "packs": ["transit", "tourism", "antifraud"],
  "toolsExclude": [],
  "defaultLocation": { "lat": 25.033, "lon": 121.565, "label": "民宿" },
  "knowledge": [{ "type": "faq", "id": "kb_12", "items": 18 }],
  "suggestions": { "zh-TW": ["怎麼去台北 101？"], "en": ["How do I get to Taipei 101?"] },
  "channels": { "web": true, "embed": true, "qr": true, "line": false, "mcp": false },
  "model": "claude-haiku-5-5",
  "limits": { "messagesPerDay": 2000 },
  "effectiveTier": "L2"                                    // 由選用工具包自動計算
}
```

驗證：以 zod schema 檢查；`effectiveTier` 由系統計算，不接受輸入。

## 7. Builder 流程

1. **選範本**：旅宿接待、店家客服、通勤助理、社區防詐、企業申辦助理（L3，需審核）
2. **選工具包**：顯示每個工具包的分級與會自動加入的護欄
3. **設定**：名稱、角色描述、語言、預設地點
4. **加入知識**：FAQ 表單或上傳文件（大小與格式限制）
5. **測試**：沙盒對話＋自動評測（每個範本一組必過問題，例如「怎麼去機場」必須呼叫交通工具並標示來源）
6. **發布**：L1 立即上線；L2 上線＋抽樣；L3 送人工審核。取得網址、內嵌碼、QR code

## 8. 多租戶、額度與收費（草案）

| 方案 | 對象 | 內容 |
|---|---|---|
| 民眾 | 所有人 | 免費使用第一方 agent |
| Builder 免費 | 個人、小店家 | L1 工具包、每日訊息上限、顯示平台品牌 |
| 商業 | 中小企業、民宿、旅行社 | 較高額度、L2 工具包、移除品牌、內嵌、分析報表 |
| 夥伴／政府 | 機關、大型企業 | 客製工具包、L3、SLA、專屬額度 |

計量單位：對話數、模型 token、TDX 等外部 API 呼叫。每個 tenant 與 agent 分開計量與限流；全站另設每日預算上限。

## 9. 通路

| 通路 | 說明 | 注意 |
|---|---|---|
| 網頁 | `/a/:agentId` | 預設 |
| 內嵌對話框 | 一行 `<script>` | 限制可嵌入的網域 |
| QR code | 掃了直接開對話，適合民宿、店家、車站 | 印刷後網址不可變 |
| LINE | 建立者連結自己的 LINE 官方帳號 | 頻道金鑰由建立者提供、加密保存 |
| MCP 端點 | `/mcp/a/:agentId`，給 Claude 等 client | 只暴露該 agent 的工具 |
| iOS / Android App | App 內的 agent 清單；可用裝置端工具（定位、提醒） | 依 ADR-0008 的卡片契約與事件協定 |
| API | 開發者用 | API 金鑰、用量儀表板 |

多語：先支援繁中、英文、日文、韓文。tool 輸出保留來源提供的英文名稱（TDX 多數站名有英文）；卡片文字在地化；L3 內容只提供中文原文＋翻譯參考。

## 10. 啟動門檻（全部達成才開始 M9）

| 門檻 | 標準 |
|---|---|
| 第一方 agent | 至少 2 個上線（生活＋反詐騙），tool 成功率 ≥ 99%，連續 8 週無重大護欄事故 |
| 需求驗證 | 至少 5 家設計夥伴（民宿、店家、旅行社、企業）有具體用例並願意試用 |
| 單位經濟 | 每次對話成本已知（模型＋外部 API），初步定價經夥伴驗證 |
| 護欄 | L2 護欄（反詐騙）在真實流量下驗證過，輸出檢查器上線 |
| 法務 | 完成下列「未決問題」中的法律與條款確認 |

## 12. 未決問題（需在 M9 前回答）

1. **TDX 條款**：以我們的金鑰服務第三方建立的 agent，是否符合 TDX 使用規範與訂閱方案？需要什麼方案？
2. **責任歸屬**：建立者的 agent 給錯資訊時，平台與建立者如何分責？服務條款怎麼寫？
3. **個資**：建立者上傳的知識、對話紀錄存哪裡、存多久？是否需要個資法相關告知與同意？
4. **模型供應商條款**：以平台形式提供給第三方使用，商業條款與使用政策需逐項確認。
5. **品牌**：「阿幫」商標是否可用？與台灣大哥大品牌的關係？
6. **第三方工具包**：是否開放夥伴提交工具包？認證流程與責任？
7. **競爭定位**：與 TDX 官方 MCP、民間資料 MCP Hub、通用型 agent builder 的差異是否足夠（我們的主張：可信的台灣工具包＋分級護欄＋互動卡片＋在地通路＋電信觸及）。
8. **旅客通路**：能否與旅客上網方案、機場、旅宿通路結合？

## 13. 指標

已發布 agent 數、每週活躍 agent 數、對話數、tool 成功率、護欄觸發與違規數、每次對話成本、付費 tenant 留存率。

## 14. 主要風險

| 風險 | 對策 |
|---|---|
| 先蓋平台沒人用 | 啟動門檻＋設計夥伴先行 |
| 建立者做出錯誤或有害的 agent，品牌受損 | 分級護欄不可關閉、L3 人工審核、可下架、稽核紀錄 |
| 外部 API 額度被少數 tenant 用光 | 每 tenant 額度、快取共享、全站預算 |
| Prompt injection（來自建立者知識或使用者） | 知識當資料、固定組裝順序、輸出檢查 |
| 多語內容品質 | 先上 4 種語言；L3 只給中文原文 |
