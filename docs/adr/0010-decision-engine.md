# ADR-0010：依「MCP 資料＋使用者狀態」做決策，規則透明、由程式計分

狀態：已採用（2026-11-17）；實作 `core/decide.js`、測試 `test/decide.test.js`、原型 `docs/prototypes/transit-discussion.html`

## 背景
Austin 的要求：MCP 資料回來後，阿幫要依**資料與使用者狀態**判斷並給出最佳決策，而且決策過程要有動畫、看得懂。考量要包含價格與交通狀況（例如塞車就建議台鐵或高鐵），YouBike 保留，叫車之後可串 Uber。

## 決策
1. **分工**
   - 工具（MCP）：提供事實（時間、班次、價格、車數、路況、天氣）。
   - 決策引擎 `core/decide.js`：純函式、規則透明、可測試，替方案計分排序並產生理由句。**不經模型**。
   - 模型：判斷使用者狀態（從對話）、決定要問哪些工具、用口語轉述結果。不自行計分或改寫分數。
2. **比較項目**（都是越小越好）：總時間、等車、走路、費用（以「最佳值／本方案」比例計分，不被極端值壓扁）、淋雨、體力、塞車風險（0–1 程度值）。
3. **使用者狀態**調整權重：趕時間、塞車中、下雨、帶行李、想省錢、少走路、空品不佳（M10）。狀態來源三種，畫面上要標示：
   - **自動判斷**：由 MCP 資料推得（天氣回報下雨 → 下雨；路況回報壅塞 → 塞車中；起點空品 AQI > 100 → 空品不佳）
   - **你說的**：從對話取得（「10 點前要到」→ 抵達時間限制；「我帶著行李」→ 帶行李）
   - **你選的**：使用者在畫面上點選
4. **硬限制**：指定抵達時間時，會遲到的方案直接排除並說明。
5. **決策過程動畫：決策圖**（淺色、交通語意，參考影片的「節點與流動」手法但不移植其風格）
   - ① 收集資料：左側是本次用到的資料來源（地點、天氣、路況、公車、YouBike、高鐵、台鐵、票價、叫車），每個來源回報時，一個帶著真實數值的資料膠囊（例：「小雨」「12分到」「8台」）沿線流向中間的阿幫。
   - ② 看你的狀況：狀態標籤浮現在阿幫上方，並以虛線連回推得它的資料來源（天氣 → 下雨・自動）；「你說的」條件同時顯示。
   - ③ 比較：阿幫到右側各方案的連線依分數逐項變粗；會遲到的方案變成紅色虛線並標「遲到」。
   - ④ 決定：最佳方案亮起並持續有光點流動；左側「讓它勝出的資料來源」同步亮起（例如下雨時亮天氣、塞車時亮路況），其餘淡出；下方一句理由。
   - 切換狀態即時重算並重播 ③④；逐項分數長條收在「看比較細節」。
   - 原則：畫面上的數字與連線都來自真實資料與 `core/decide.js` 的結果，不做裝飾性的假流動。
6. **方案來源可擴充**：公車、YouBike、步行、捷運、台鐵、高鐵、國道客運、叫車（Uber 等，以 provider adapter 介接，先做深層連結，估價 API 待合作）。

## 影響
- `plan_trip` 輸入加 `prefs`（狀態與抵達時間），輸出 `ranking`（含 breakdown 與 reason）；網頁與 MCP Apps 卡片都依此畫動畫。
- 事件協定新增 `decision`（`AGENT.md` §3.1）。
- 權重屬於產品決策，調整需更新測試並記錄於本 ADR。

## 權重調整紀錄
- 2026-11-22：非權重調整、記錄供參——捷運加營運時間（`METRO_HOURS`，⚠️ 大約值、以各系統公告為準）：收班時段（台北約 00:00～06:00）不列入候選方案、收班前 30 分列入但提醒末班；真實模式公車因 TDX 額度用完改用示範資料時，公車也依時間估收班（00:00～05:00）。原因：產品負責人 00:10 問「去台北101」，示範資料仍推捷運（實際已收班），公車與捷運沒列入的原因也看不到。沒列入的方式與原因改成任何時候都輸出（`missing`），深夜的一句（`night`）放在回答第一句。測試：`test/trip-night.test.js`。同日審查修正：營運判斷看走到站的時刻；明天＋抵達時間合成的出發時間不早於 06:00（原本最早 05:00，「明天早上9點前」會把捷運當收班而改推叫車）；只給 HH:mm 且早於現在 1 小時以上視為明天。
- 2026-11-18（M3-11）：「想省錢」`cost` 倍數 3 → 5。原因：市區短程（台北車站→台北101）叫車約 255 元、公車 15 元，×3 時兩者同分、叫車以時間較短勝出，不符合「想省錢」。×5 時公車第一、叫車最後；跨城（新竹）仍是客運第一。測試：`test/decide.test.js`「想省錢」、`test/trip-od.test.js`。
- 2026-11-18（M5-13）：非權重調整、記錄供參——班次制方案（軌道、客運）的等車最多算 10 分（再多視為晚點出門），避免很早出發時總時間被等車灌水；跨城＋塞車情境的最後一名因此從客運變為叫車（`test/trip-od.test.js`）。
- 2026-11-19（M10）：新增狀態「空品不佳」`badAir`（`exposure` ×3、`effort` ×2），`plan_trip` 起點最近測站 AQI > 100（對敏感族群不健康以上）時自動加入；比較項目 `exposure` 標籤由「淋雨」改為「戶外」（下雨淋雨、空品差吸髒空氣都算），理由句只有空品不佳且沒下雨時說「少待在戶外」。市區短程＋空品不佳：叫車第一、步行最後（`test/trip-od.test.js`）；西門町→101 三方案：公車第一（`test/decide.test.js`）。
- ~~待 Austin 決定~~（2026-11-21 已決定，見下一條）：無狀態時市區短程（1.5～5 公里）叫車排第一（走路 0、淋雨 0、體力 0 的優勢大於約 250 元的費用差）。若希望預設偏向大眾運輸，可提高 `cost` 基本權重或降低 `walkMin`；改了要同步 `test/trip-od.test.js`。
- 2026-11-21：Austin 回饋「點去 101 幾乎都是叫車」「會不會以後都只推薦叫車？要更聰明一點」。決定：**沒有任何狀態時以大眾運輸為主，有理由才推叫車**。
  - 基本權重：`cost` 0.15 → 0.20、`walkMin` 0.15 → 0.12、`exposure` 0.10 → 0.03、`effort` 0.10 → 0.05。原因：叫車在等車、走路、戶外、體力四項永遠最好（原本合計 45%），費用只佔 15%，無狀態時 11 種常見起訖有 10 種推叫車。
  - 戶外與體力的基本權重降了，相關狀態倍數等比例調高，狀態下的行為不變：`rain` exposure ×4 → ×13、`rainSoon` ×2 → ×7、`badAir` exposure ×3 → ×10、effort ×2 → ×4；`luggage` effort ×4 → ×8；`lessWalk`、`elder`、`kids` effort ×3 → ×6；`mobility` effort ×4 → ×8；`group` effort ×1.3 → ×2.6（否則下雨、空品差、帶行李會推騎 YouBike）。
  - `budget` cost ×5 → ×3（費用基本權重提高後，×5 會讓「想省錢」推走路 100 分鐘）。
  - 結果（示範資料，台北車站／西門町／板橋 → 台北101、松山機場、故宮）：無狀態推捷運或公車；趕時間、帶行李、下雨、帶長輩推叫車；想省錢推公車。台北車站→松山機場無狀態仍推叫車（示範資料沒有捷運方案，公車 1503 較慢）。
- 2026-11-21（個人化）：Austin：「個人化，記住我常選的」。新增**習慣**（`ctx.habit`，非權重倍數，是小幅加分 `breakdown.habit`）：
  - 記什麼（只在手機，`public/js/habits.js`，localStorage `abang.habits`）：使用者實際「選了」的交通方式角色與時間——行程卡按建議方案的導航／叫車／訂票、說或按「改成 X」（含決策圖點方案）、設公車到站提醒或下車提醒。不記地點、路線、站名；最近 50 次、60 天半衰期、180 天前不算；30 分鐘內同一種方式只算一次；選滿 5 次才生效。隨請求只送各方式比例 `userState.habit`（例 `{ metro: 0.6, bus: 0.3 }`），伺服器 zod 驗證（鍵限定 8 種方式、值 0～1、總和 ≤ 1.01），由程式帶進 `plan_trip` 的 `prefs.habit`（模型帶的一律不採用）。
  - 怎麼加分：`HABIT = { max: 0.08, full: 0.6 }`——常選比例 ≥ 60% 加滿 **8 分**（滿分 100），比例越低越少（60% 捷運＋40% 公車 → 捷運 +8、公車 +5.3，混著選的人差距自然變小）。
  - 優先順序：使用者指定方式（`mode`）、說不要（`avoid`）、抵達時間（`arriveBy` 會遲到的照樣排除）都在習慣之前；**使用者說了（或點選了）狀態（`said`：狀態 source 不是 auto）時，這次不看習慣**；自動判斷的狀態（下雨、塞車）不擋習慣。比最快的方案慢超過 2 倍且多 20 分以上的不加分（走路 100 分鐘不會因習慣勝出）。
  - 為什麼是 8 分：示範資料常見起訖的第一、二名多差 3～7 分；+4 分時「常搭捷運」的人從西門町去台北101 仍推公車（74.6 對 67.7），不像「記住我常選的」。8 分會翻轉這種接近的比較，差距大時不翻盤（台北→高雄常叫車仍推台鐵 84 對 54）。
  - 理由句：勝出方案有習慣加分時以「你常搭捷運」開頭（「選「捷運 淡水信義線」：你常搭捷運、省 230 元、不受塞車影響。」）；決策圖有「你常選：捷運」chip（source habit，可點掉即時重算，旁邊「為什麼」看次數）。
  - 結果（示範資料）：常搭捷運 → 西門町→101 由公車改推捷運；常叫車 → 台北車站／板橋→101 改推叫車（ridehail 這點屬產品決策，見下）；台北→高雄、新竹不變。測試：`test/decide-habit.test.js`、`test/habits.test.js`。
- 2026-11-21（互動確認，取代上一條的「默默加分」）：Austin：「如果多問使用者來判斷應該比較好，重要因子應可與用戶互動後完成。」原則：**不默默套用推測，在關鍵時刻問使用者一句**（機制見 ADR-0016）。
  - 習慣：記錄照舊（只在手機、只記方式與時間，記錄預設開——只記不用、不影響建議）；某方式 ≥ 5 次且佔 6 成以上時，那一輪問「我注意到你最近常搭捷運（6 次）。以後你沒說條件時，要我優先推捷運嗎？」〔好（猜的）〕〔不用〕。**說「好」才把該方式送進 `userState.habit` 加分**（上限與規則照上一條：最多 8 分、說了狀況／指定方式／不要／抵達時間優先、太慢的不加分）；說「不用」90 天內不問；設定頁「已同意：優先推捷運」可撤銷。決策圖 chip 改為「你同意：優先推捷運」，理由句「你想優先搭捷運」（只有拿掉偏好加分會換第一名時才說）；未確認的習慣不顯示 chip、不加分。
  - 叫車另外問原因（有理由才推叫車）：「你常叫車（N 次），通常是因為？」〔趕時間〕〔常帶東西〕〔不想走路〕〔就是喜歡叫車〕〔不一定〕。前三個存成「你說過」的預設狀況（`userState.usual`），**不自動套用**：這一輪沒說條件、而且加上它會換建議時，問「這次也帶東西嗎？」〔是（猜的）〕〔這次沒有〕，點〔是〕才加上那個狀態即時重算、決策圖出現「你說過：常帶東西」；設定頁列出可撤銷。「就是喜歡叫車」才給叫車習慣加分；「不一定」不加分、不再問。
  - 關鍵因子：`keyQuestion`（純函式，伺服器與前端共用）試加上趕時間、想省錢、帶行李、少走路各一個狀態重算；建議會換、而且時間差 ≥ 5 分或費用差 ≥ 50 元才問（挑影響最大的一個，例「叫車快 5 分但多 270 元，你趕時間嗎？」〔趕〕〔不趕〕）；點〔趕〕＝加上 rush 即時重算（不呼叫伺服器）。使用者已經說了狀況、指定方式、任何狀態都不會翻盤時不問；**同一段起訖（座標到小數 2 位）同一題 24 小時內只問一次**（出現就算，點了〔不趕〕也是；手機只存那一題的雜湊，最多 50 筆），換地點或隔天才再問。測試：`test/ask.test.js`。
