01 · OVERVIEW

專案概覽

阿幫是串接台灣政府開放資料的 AI 助手。第一階段聚焦大眾交通，網頁優先：一組可被任何 AI agent 使用的交通 MCP tools，加上一個會「找小幫手討論、依你的狀況做決定」的民眾網頁 agent。

民眾

網頁 agent

一句話問交通，不需要 Claude 帳號。看得到小幫手討論與決策圖，結論卡片可直接導航、訂票、叫車。

Claude 使用者

遠端 MCP 連接器

在 Claude 加入自訂連接器 /mcp，就能查公車、YouBike、高鐵台鐵、規劃行程，卡片一樣能互動。

開發者

開放的 MCP server

stdio 或 HTTP 接入自己的 agent；工具依工具包（pack）與風險分級（tier）組合。

    04 · OPEN DATA

    Open Data 來源與使用方式

    交通資料來自交通部 TDX 運輸資料流通服務；決策用的天氣來自中央氣象署；導航、訂票、叫車用官方深層連結。完整清單見 docs/DATA_SOURCES.md。

    申請 TDX 金鑰

    1. 到 TDX 官網註冊會員並完成 Email 驗證，等待管理員審核。
    2. 登入後到「會員中心 → API 金鑰」取得 Client Id 與 Client Secret（最多 3 組）。
    3. 放進專案根目錄的 .env（不要進版控）：
      TDX_CLIENT_ID=你的ID
TDX_CLIENT_SECRET=你的Secret
    4. 執行 npm start，畫面上方的「示範模式」提示消失即代表已使用真實資料。

    認證方式

    TDX 使用 OIDC Client Credentials：先換 Access Token（有效 24 小時），之後每次呼叫帶 Authorization: Bearer。專案已在 core/tdx-client.js 實作快取與到期前自動換新。

    curl -X POST https://tdx.transportdata.tw/auth/realms/TDXConnect/protocol/openid-connect/token \
  -H 'content-type: application/x-www-form-urlencoded' \
  -d grant_type=client_credentials -d client_id=$TDX_CLIENT_ID -d client_secret=$TDX_CLIENT_SECRET

    05 · AGENT LINEUP

    Agent 產品線

    同一個平台上跑多個 agent。每個 agent 只是「一組 tools + 一份 system prompt + 知識庫 + 護欄」的設定，核心、卡片、MCP 出口、限流全部共用。交通 agent 先把平台做穩，其他 agent 再陸續上線。

    阿幫・生活

    公車、捷運、YouBike、台鐵高鐵、從 A 到 B 怎麼去。之後擴充天氣、AQI、藥局。

    阿幫・防詐

    06 · LIFE AGENT

    阿幫・生活

    民眾不需要懂 MCP，也不需要 Claude 帳號：在網頁一句話問交通，阿幫找小幫手討論、依「即時資料＋你的狀況」做決定，給一張可以直接出發的結論卡片。

    互動原型

    四個情境：西門町到台北 101（自動偵測下雨 → 公車；關掉下雨 → YouBike）、明早 8 點前到左營（會遲到的班次排除）、塞車時去新竹（台鐵自強勝出，可叫車）、307 到哪了（即時倒數）。資料為模擬。

    在新分頁開啟原型 →　正式實作由真實事件驅動，不照抄原型的假資料與等待時間。

    一次對話會發生什麼

    1. 理解：判斷意圖、地點與你說的狀況（「8 點前要到」「帶行李」）。Claude 模式由模型判斷；示範模式用規則。
    2. 點名小幫手：阿幫說一句「我請 @公車 @YouBike @天氣 看看」，可平行呼叫。
    3. 小幫手回報：每個工具用一句話回報真實資料（speak，不經模型），標示 tool 與 MCP 來源；討論完收合成一行。
    4. 決策圖：資料膠囊流入 → 狀況標籤連回資料來源 → 方案依分數排序、線條變粗 → 勝出路徑亮起，附一句理由。
    5. 結論卡片：建議方案、分段時間條、備案；導航、提醒、訂票、叫車一鍵完成；倒數即時更新。

    小幫手討論串：看得到多 MCP 怎麼配合

    MCP 之間其實不會直接對話——是阿幫依前一個工具的結果決定下一步；討論串是這些真實呼叫的忠實呈現：阿幫的話＝agent_note、@工具＝tool_start、工具的話＝tool_result.speak。數字都來自真實資料，不加假延遲（ADR-0009）。

    依資料與你的狀況做決策

    你的狀況怎麼得知影響
    下雨自動：weather_now淋雨權重 ×4、走路 ×1.5 → 偏向公車、捷運
    塞車中自動：traffic_status，或你說的塞車風險權重 ×6 → 偏向台鐵、高鐵；客運、叫車延誤
    趕時間你說的／你選的總時間 ×2、等車 ×1.5、塞車風險 ×2
    帶行李你說的／你選的體力 ×4 → 少轉乘、少騎車
    想省錢你說的／你選的費用 ×3
    少走路你說的／你選的走路 ×1.5、體力 ×3
    幾點前要到你說的硬限制：會遲到的方案直接排除

    比較項目：總時間、等車、走路、費用（比例計分）＋淋雨、體力、塞車風險（0–1）。計分由 core/decide.js 依透明規則完成，模型不自行計分；切換狀況會在前端用同一份程式即時重算（ADR-0010）。

    導航、訂票、叫車

    只產生官方連結：導航開 Google／Apple 地圖；訂票用 TDX 導訂票產生自動帶入車次的官方訂票網址；叫車先用 Uber 深層連結。訂票與叫車屬 L2，產生前要你確認，付款與個資都在官方網站完成（ADR-0011）。YouBike 照常列入比較。

    07 · ANTI-SCAM AGENT

    阿幫・防詐（構想）

    民眾收到可疑簡訊、LINE 訊息或投資邀約時，貼上來就能得到風險判斷、可疑之處的說明，以及下一步該怎麼做。電信業者本身就站在防詐第一線，這條產品線與台灣大哥大的角色最貼近。

    試試看：貼上一則可疑訊息

    示意版只用關鍵字規則；正式版會結合 165 開放資料比對與模型判斷。黑名單比對為示範資料。

    可運用的資料與機制

    資料／機制來源用途
    165 詐騙 LINE ID內政部警政署（政府資料開放平臺，欄位：LINE ID、通報日期）比對訊息中的 LINE ID
    165 假投資（博弈）網站、詐騙闢謠專區內政部警政署（政府資料開放平臺；更新頻率待確認）比對網址、提供闢謠說明
    111 政府專屬短碼簡訊數位發展部；政府機關簡訊由「111」發送，電信業者也有各自短碼（台灣大哥大為 935）宣稱是政府但不是 111 發送 → 提高風險
    常見詐騙手法特徵165 宣導內容整理成規則庫（人工維護）假投資、解除分期、假冒機關、假包裹等特徵

    MCP tools 構想

    Tool用途
    scam_check_message分析訊息文字：比對特徵規則、抽出網址／LINE ID／電話，回傳風險等級與理由（卡片：風險量表 + 標示可疑字句）
    scam_lookup_lineid / scam_lookup_url比對 165 開放資料清單
    sms_sender_check判斷寄件號碼是否為政府或電信業者短碼
    scam_myth_search搜尋 165 闢謠內容

    必要的護欄

    • 永遠不說「這則訊息是安全的」；查無紀錄只代表「未在已知清單中」。
    • 高風險時第一個動作是引導撥打 165 反詐騙諮詢專線，不要求使用者回覆或點擊任何連結。
    • 貼上的內容不儲存、不寫 log；統計只記錄詐騙類型與時間，可回饋給主管機關作為趨勢參考。
    • 網址只做字串比對與解析，不由伺服器主動開啟可疑連結。

    09 · GOV EFFICIENCY

    強化政府效率的延伸方向

    除了讓民眾查得更快，同一套「開放資料 → MCP → agent」架構也能減少政府端的重複工作。以下依可行性排序，皆為候選方向，尚未排入開發計畫。

    市場現況（2026-11）：交通部 TDX 已推出官方 MCP（臺鐵／高鐵班次與票價、道路事件，遠端 HTTP、需會員金鑰）；民間也有涵蓋約 4.9 萬筆 data.gov.tw 資料集與政府採購資料的 MCP Hub。本專案的差異化應放在跨資料組合的工具（如行程規劃）、互動卡片與免帳號的民眾 agent，單純包裝 API 的價值有限。
    方向資料或串接方式對政府的效益可行性
    民眾問題需求報表agent 查詢紀錄（去識別化、只留縣市／路線層級）交通局看到「哪些路線常被問、末班車後仍有需求、哪裡常查不到車」，作為班次調整依據高 自有資料，M5 後即可做
    道路事件與施工主動通知TDX 官方 MCP 道路事件、各縣市道路挖掘／施工開放資料民眾事先繞道，減少 1999 與警察局的路況詢問高 資料已開放
    「怎麼申辦」問答附法源全國法規資料庫、各機關申辦須知（data.gov.tw）減少櫃台與電話重複詢問；回答附條文出處，降低錯誤資訊中 需嚴格引用與免責
    結構化陳情通報1999 派工項目與處理時限（公開）；送件需與縣市政府合作介接agent 先問清楚地點、類別、照片再送出，減少客服轉派與退件需合作 目前無公開送件 API
    地址轉座標標準化內政部 TGOS 地理編碼服務（需申請）民眾說的地址可直接對應門牌座標，通報與查詢更精準中 需申請金鑰
    MyData 帶入個人資料數發部 MyData（民眾授權後帶入戶籍、財產、所得等）例如社宅申請已可線上辦理、免紙本；未來可縮短申辦流程觀察 目前以政府機關為主，數發部表示將擴大到國營事業與金融機構
    提供 tools 給機關內部 AI數發部 TryAI（公務 AI 平台，機關 Bot 可用 API 串接內部系統）機關的公務 Bot 也能查即時交通，回覆民眾更快觀察 目前未見 MCP 支援
    電信人流 × 交通資料去識別化人流統計結合 TDX 班次與運量找出運能不足的時段與路段，支援公車路網調整內部評估 需公司資料治理與法遵確認

    建議的下一步

    1. M5 上線時就設計好去識別化的查詢統計（只記 tool 名稱、縣市、路線、時段），為「需求報表」留資料。
    2. M3 評估是否直接介接 TDX 官方 MCP 的道路事件，或呼叫對應 REST API，納入 plan_trip 的提醒。
    3. 找一個縣市交通局或 1999 單位做小型合作，驗證需求報表與結構化通報的價值。

    參考：TDX 官方 MCP、MCP Hub 報導、數發部 TryAI、MyData 社宅申請報導、1999 派工項目及處理時限表、TGOS。

      Claude Code 循環開發

      每輪做一個任務：讀狀態 → 選下一個任務 → 讀該任務必讀文件 → 實作與測試 → 更新文件 → 勾選與紀錄 → commit。遇到金鑰、權限、新依賴、ADR 變更就停下來問。

      你是阿幫（A-Bang）專案的開發者。照 docs/LOOP.md 的協定做「一輪」：
1) 讀 CLAUDE.md、docs/PLAN.md 狀態看板、docs/PROGRESS.md 最後 5 筆、git status。
2) 若有上一輪未完成的變更，先收尾（npm test 通過後提交），本輪就結束。
3) 否則選 PLAN.md 目前里程碑第一個未勾選、未標 ⛔ 的任務，只讀 LOOP.md §3 列的必讀文件。
4) 實作＋測試（npm test 全過；有 UI 就用 Playwright 截圖自己檢查），同步更新規格文件。
5) 在 PLAN.md 勾選並更新狀態看板，在 docs/PROGRESS.md 最上面加一筆紀錄，git commit（不要 push）。
6) 遇到 LOOP.md §2 的停止條件就停下並說明需要我做什麼。
最後用 3–5 行回報：完成的任務代號、測試數、下一個任務、卡住事項。
