## P0（優先處理：直接影響準確率與額度）

### 1. 串接 TDX 地理編碼進 `find_place`（＋地標校對）
- **現況問題**：`core/data/landmarks.json`（230 筆）多為近似座標；而 `docs/PLAN.md` 已紀錄 M1 實測確認 TDX `/advanced/V3/Map/GeoCode/Coordinate/Address/{地址}` 與 `/Markname/{地標}` 可用，但尚未串進 `find_place`。
- **風險**：起訖點座標只要偏掉，後續的「最近公車站／YouBike／步行時間／捷運站」全都會跟著失準，也是民眾最容易覺得「阿幫不準」的地方。
- **建議作法**：
  1. 在 `find_place` 加入 fallback 鏈：`內建精確地標 (verified) → 快取 → TDX 地理編碼（地址優先、地標次之）→ 近似地標`。
  2. 對 TDX 地標回傳多筆的情況（`PLAN.md` M1 已註記「第一筆不一定是本身」），加入名稱相似度排序與台灣範圍（經緯度邊界）防呆。
  3. 同步保留對應 mock 與快取 TTL，符合 `CLAUDE.md` 架構規則。

### 2. 解決 `T-QUOTA`（降低單題行程對 TDX 的呼叫次數）
- **現況問題**：TDX 每分鐘 5 次額度相當緊繃；`docs/PLAN.md` 待辦已點出 `core/agent/run.js` 在行程題會先呼叫 `traffic_status`，接著 `plan_trip` 又查一次。
- **建議作法**：
  1. 行程規劃類意圖直接走 `plan_trip`（其本身已含路況評估並輸出 `considered`），避免 agent 流程重複先打 `traffic_status`。
  2. 強化額度耗盡／429 降級時的對外文案：清楚告訴使用者「目前即時資料暫用快取／時刻表推算」，避免讓使用者誤以為功能故障。

## P1（讓 Agent 真正「聰明且貼心」）

### 3. 務實版多運具接駁：`T-MIX` 先做「兩段式模板」
- **現況問題**：`plan_trip` 已有台鐵換車與完整捷運路網轉乘，但起訖點附近無捷運站時（如三峽、林口、桃園高鐵站 → 台北市區），公車／YouBike 與捷運尚未串成聯運方案。
- **建議作法**：不需一開始就實作全圖多運具路徑搜尋，建議先收斂為兩個高頻兩段模板：
  1. `YouBike／市區公車 → 最近捷運站 → 捷運`
  2. `台鐵／機捷 → 轉乘捷運`
  - 延續 `core/decide.js` 計分機制（ADR-0010），將轉乘步行距離與等車時間納入懲罰權重。

### 4. 本機「輕量偏好記憶」（不進伺服器、符合隱私原則）
- **現況問題**：目前已有對話保留與「該問就問」，但使用者每次查行程仍常需重複表達個人限制（例如：下雨不想騎車、怕走路、習慣早到）。
- **建議作法**：
  - 在裝置端（`localStorage` 或設定架構內）以透明、可清除的方式記錄低敏感度偏好（如常用排序傾向：省時／少走路／省錢）。
  - 下次問行程時不強制覆蓋，而是作為預選狀態或輕聲確認（例：「照上次一樣優先少走路嗎？」），並可在設定頁一鍵關閉或重置。

### 5. 行程中模式 v2：異常主動給 B 方案
- **現況問題**：已有行程中列與下車提醒，但「進行中遇到突發狀況」的應變能力還可加強。
- **建議作法**：
  - 在行程進行中若偵測到目標公車明顯延誤、或前方國道路況惡化，主動推送一張「替代 B 方案」建議卡（例如改步行去捷運站或改借 YouBike），讓阿幫從「查時刻表工具」升級為「隨身應變助手」。
